# Semantic Endpointing — P2.01 Build Log

**Task:** P2.01 · VAD · P0 &nbsp;|&nbsp; **Owner:** Nikhil &nbsp;|&nbsp; **Branch:** `P2-01/semantic-endpointing`
**Status:** validated — ship **on @ 200 ms** &nbsp;|&nbsp; **Updated:** 14 Sep 2026

How we cut the VAD end-of-turn wait — the biggest single latency cost in the voice agent — from a
first build that failed on real calls, through the finding that reshaped it, to a validated
production setting. Written so the next engineer can see not just what we shipped, but *why it isn't
what the task sheet first described.*

---

## 00 · The task, as written

From the task sheet: *"Semantic endpointing: stop_secs 700 ms → 120 ms with word-count guard."*
Target **−580 ms TTFA** (≈42% of total), accuracy −2%, file `voice_ws.py`.

The note said: change `DEEPGRAM_ENDPOINTING_MS=120`, extend `MinWordsUserTurnStartStrategy` to a
1‑word guard during silence to stop "yes"/"ok" false triggers, and **test with real call recordings
before rollout.**

The pipeline already had a dormant piece to build on: **Smart Turn**, a small local model (bundled
with pipecat, ~12 ms CPU) that judges from the audio itself whether an utterance sounds finished —
the "semantic" in semantic endpointing. It shipped off, at a conservative 350 ms window.

---

## 01 · The journey, step by step

### 1. Build (v1) — the literal-ish version
Built semantic endpointing the safe way the sheet implied, off by default:

- A *separate* `SEMANTIC_ENDPOINTING_MS` (120) rather than overwriting the tuned 700 ms
  `DEEPGRAM_ENDPOINTING_MS`.
- Smart Turn built whenever semantic endpointing is on — the short window is only safe with a
  semantic completeness check behind it.
- A turn-boundary **word-count guard** to hold lone "yes"/"ok" fragments.
- A decision trace (`endpointing-trace`) for debuggability.

### 2. Test @ 120 ms — real calls exposed two failures
Exactly what "test on real recordings" is for. The traces showed:

- **Smart Turn misfired.** At a 120 ms window it is starved of trailing silence and hedges to
  `INCOMPLETE` on finished turns ("Yes.", "registered? Can you give that again?") — each costing a
  flat ~900 ms hold. Net latency was a wash‑to‑worse on ~half of turns.
- **Dictation shattered.** The grace windows (0.8–0.9 s) were shorter than real dictation pauses
  (0.9–2 s), so phone numbers split into 3–4 turns and "My name is" detached from "Rahul".

### 3. Find — the root cause: the window starves the model
A control run with Smart Turn alone at 350 ms returned `COMPLETE` reliably and flowed cleanly. Same
model, same phrases, opposite verdicts — proving the 120 ms window itself was degrading Smart Turn.
**120 ms sits below this local model's usable floor.** This is the finding that reshaped the task.

### 4. Change (v2) — decouple from the model's noise
Instead of forcing 120 ms and fighting the misfires, we made the logic robust to them:

- **Corroboration.** An `INCOMPLETE` verdict only *holds* when the transcript *itself* looks
  unfinished (a dangling connector, bare digits, a number mid‑dictation). A finished‑looking clause
  the model misflagged is overruled and runs at once — killing the 900 ms tax.
- **Dictation-aware grace.** Corroborated holds use a longer, re‑arming window (1500 ms, 4000 ms
  ceiling) so a name or number said in groups merges into one turn.
- **Word-prefixed numbers.** "my phone number is 8 0 7 8" is recognised as a number still in
  progress, not run on a half‑number.
- **Dropped the word-count guard** — it would have held every "yes"/"ok" for 1.5 s, gutting the win.
  That case is already handled upstream by `MinWordsUserTurnStartStrategy`.
- Added an `endpointing-timing` debug line to measure the real cost, and 15 unit tests for the
  decision logic.

### 5. Validate — swept off / 200 ms / 120 ms on live calls
**200 ms won** (see the table below). Set as the production default.

## 02 · The three configurations, measured

All from live DSR Infra booking calls (Hinglish + English, browser mic).

| Behaviour | OFF (baseline) | ON @ 120 ms | ON @ 200 ms |
|---|---|---|---|
| VAD window | 700 ms | 120 ms | 200 ms |
| Endpointing total (normal turn) | ~980 ms | ~419 ms | ~490 ms |
| vs baseline | — | −561 ms | −490 ms |
| Phone-number capture | **fails** — only "9986", escalated | **shaky** — single-digit shatter, mashed reply | **merges** — registered first try |
| False 900 ms holds | n/a | frequent | none |
| Overall reliability | worst | borderline | **production** |

> **Why 200 ms is the pick.** 120 ms saves only ~70 ms more than 200 ms (419 vs 490) yet brings the
> dictation-shatter back; OFF regresses number capture so badly a call escalated. 200 ms captures
> **~93% of the maximum latency win with production-grade reliability** — the honest sweet spot for
> this model.

## 03 · What the timing debug shows

The `endpointing-timing` line (gated on `ENDPOINTING_TRACE_ENABLED`) reports the real cost per turn:
`window` (the configured silence wait) + `finalize_hold` (STT finalize + any hold) = `total`.

```
# ON @ 200 ms -- normal turns sit at ~490 ms, dead consistent
endpointing-timing window_ms=200 finalize_hold_ms=284 total_ms=484 text='flat'
endpointing-timing window_ms=200 finalize_hold_ms=305 total_ms=505 text='okay'

# ON @ 120 ms -- ~70 ms faster, but dictation gets shakier
endpointing-timing window_ms=120 finalize_hold_ms=299 total_ms=419 text='...'

# a corroborated dictation hold -- larger by design, waiting to merge
endpointing-timing window_ms=200 finalize_hold_ms=1520 total_ms=1720 text='my phone number is ...'
```

`finalize_hold` is a fixed ~280–300 ms floor (STT finalize + Smart Turn) unaffected by the window —
attacking that is STT/region work (P3.06), not this task.

## 04 · What we built vs the task sheet

Same intent, three corrections the real calls forced:

| Task sheet said | What we shipped |
|---|---|
| Set `DEEPGRAM_ENDPOINTING_MS=120` (reuse the existing var) | A *new* `SEMANTIC_ENDPOINTING_MS` — leaves the tuned 700 ms fallback intact and reversible |
| Window = 120 ms | Window = **200 ms** (120 ms is below the model's reliable floor) |
| Word-count guard in `MinWordsUserTurnStartStrategy` for "yes"/"ok" | Guard moved to **corroboration in the bridge** — the turn boundary, where it actually works; the sheet's guard only governs barge-in |
| −580 ms TTFA | **−500 ms, reliable** — traded 80 ms of the target for stability |

> The −580 ms number assumed a semantic model more capable at 120 ms than the bundled one is.
> Reaching a true 120 ms is a follow-up: a stronger / remote endpointing model.

## 05 · Configuration reference

**Enabling is one key.** Every knob defaults to its validated value, so the entire production enable is:

```bash
SEMANTIC_ENDPOINTING_ENABLED=true
```

The rest are optional advanced overrides — leave them unless retuning.

| Setting | Default | Purpose |
|---|---|---|
| `SEMANTIC_ENDPOINTING_ENABLED` | `false` | Master switch. Off = unchanged 700 ms behaviour. The only key you need. |
| `SEMANTIC_ENDPOINTING_MS` | `200` | VAD window when on. Validated production value (120 is below the model's floor). |
| `SEMANTIC_REQUIRE_INCOMPLETE_CORROBORATION` | `true` | Only hold on INCOMPLETE when the words also look unfinished. The false-hold fix. |
| `SEMANTIC_CONTINUATION_GRACE_MS` | `1500` | Re-arming hold window for dictation (name/number in groups). |
| `SEMANTIC_CONTINUATION_MAX_HOLD_MS` | `4000` | Ceiling so a trailing-off caller can never hang a turn. |
| `ENDPOINTING_TRACE_ENABLED` | `false` | Per-turn decision + timing debug logs. On only when debugging. |

## 07 · Status & what's out of scope

- **P2.01 mechanism:** built, validated, 15 tests passing. Ship on at 200 ms.
- **Latency delivered:** −500 ms endpointing per normal turn, reliable.
- **Not met:** the literal −580 ms / 120 ms — needs a stronger endpointing model (follow-up).
- **Felt latency still ~4 s** and LLM-bound (planner ~2.5 s + responder ~1.5 s) — that's
  P2.02 / P1.04 / P3.03 / P3.04, not this task.
- **Separate bugs seen in testing, not P2.01:** the planner leaking the slot name "utterance" into
  replies; Deepgram mis-detecting Spanish on some Hinglish audio; callers giving 9-digit numbers
  with no re-prompt. Each deserves its own ticket.
