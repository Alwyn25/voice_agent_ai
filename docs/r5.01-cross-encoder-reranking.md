# Cross-Encoder Re-ranking — R5.01 Build Log

**Task (R5.01):** Cross-encoder re-ranking (ms-marco-MiniLM-L-6-v2) after initial retrieval.
Owner: Nikhil. Phase 5 / P1 / RAG. Estimated effort L (3 days). Estimated gain on the sheet:
**+12% accuracy, +10–15% MRR, ~64 ms**.

**Status:** Complete. Implemented, unit-tested (37 new tests including one against the real model;
full suite 108 passed), measured on the live knowledge base with a new zero-LLM-cost retrieval eval,
and confirmed end-to-end on the 13 golden questions whose retrieval changed. **Off by default in
code**; switched on by three settings (section 07).

**Verdict in one line:** the reranker as specified did *not* help — the model is English-only and
most callers speak Hinglish, and the 64 ms estimate was ~7x too low. With two additions (a Hinglish
→ English gloss for the reranker's input, and a per-document chunk cap of 3) it does help: retrieval
**Complete@8 91.4% → 94.3%**, **MRR 0.775 → 0.813 (+4.9%)**, and end-to-end accuracy an estimated
**~+4 points** (not the +12% the sheet hoped for). On normal answer turns it adds **no
caller-visible latency**; it costs ~430 ms of CPU per knowledge question, which runs in parallel
with the classifier LLM call.

---

## 00 · The task, as written

> Current RAG uses RRF score only. Add cross-encoder that reads (query, chunk) pairs and re-scores
> using full attention. MiniLM-L-6-v2 runs on CPU in 8 ms/chunk × 8 chunks = 64 ms. Run async or on
> GPU. Fixes edge cases: "2.5 BHK price" ranking 3 BHK sheet above 2.5 BHK. Expected +10–15% MRR.
>
> Location: `core/app/engine/rag/retrieval.py` — post-RRF ranking step. Accuracy Δ: +12%.

Acceptance criteria, taken literally:

1. A cross-encoder re-scores the retrieval candidates after RRF fusion.
2. It runs fast enough not to hurt TTFA (~64 ms).
3. Retrieval ranking improves (+10–15% MRR) and answer accuracy improves (+12%).

Additional requirements from the owner: production-grade (reliable, robust), debuggable, well
commented, and **measurable without spending OpenAI credits**.

## 01 · What we actually found

### Finding 1 — retrieval was already strong; most failures are not retrieval failures

Across every past end-to-end eval run (450 graded answers, 25 Sept), 71 answers failed:

| Failure type | Count | Can a reranker fix it? |
|---|---|---|
| Forbidden / invented claim (pets allowed, "OC pending", "corpus refundable", a possession date) | 35 | No — the responder invents it |
| Incorrect fact | 15 | Sometimes (HI020 was a retrieval miss) |
| Wrongful abstention ("I don't have that") | 12 | Sometimes (EN027) |
| No answer | 9 | Rarely |

The new retrieval eval (section 03) measured the baseline at **91.4% Complete@8**: the evidence
for the answer already reaches the model on 9 of 10 questions. So the +12% on the sheet was never
available from ranking alone.

### Finding 2 — the latency estimate does not hold

Measured in the core container (AMD Ryzen AI 7 350, 4 vCPUs), 12 pairs × 256 tokens:

| Model file | 1 thread | 2 threads | 4 threads |
|---|---|---|---|
| fp32 `model.onnx` (91 MB) | 1,534 ms | 885 ms | 677 ms |
| int8 `model_quint8_avx2.onnx` (23 MB) | 615 ms | 374 ms | 323 ms |

About 30–45 ms per chunk, not 8 ms. A knowledge chunk is ~200–230 tokens, not the short passages
the estimate assumed. The int8 file is ~2.5x faster with near-identical scores, so it is the default.

### Finding 3 — the model does not understand Hinglish

`ms-marco-MiniLM-L6-v2` is trained on English only. Two-thirds of the golden questions are romanised
Hindi / Hinglish. Per language, plain re-ranking (fuse mode) versus no re-ranking:

| Language | Queries | Complete@8 off → fuse | MRR off → fuse / replace |
|---|---|---|---|
| English | 14 | 93% → 93% | 0.796 → 0.810 / **0.845** |
| Hinglish | 28 | **96% → 89%** | 0.818 → 0.804 / 0.676 |
| Hindi (romanised) | 28 | 86% → 86% | 0.720 → 0.694 / 0.631 |

It helps English ordering and pushes Hinglish evidence **out** of the window.

### Finding 4 — the multilingual model is worse, not better

`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` (multilingual) was tested as an alternative:
Complete@8 88.6% (fuse) / 85.7% (replace, significantly worse, p = 0.012), at ~750 ms per rerank
(2x slower). Rejected.

### Finding 5 — the per-document cap was hiding the one repeat failure

HI020 ("corner aur premium mein charge ka farak kya hai") failed **9 out of 9** past end-to-end
runs. The answer needs three sibling chunks from one document (corner ₹50, premium ₹75,
corner+premium ₹100 per sq ft), and the hard-coded cap of 2 chunks per document always dropped the
₹75 one, so the agent said "premium is ₹100". No ranking change can fix that; the cap had to become
a setting.

## 02 · What we built

### Pipeline

```
question
  │
  ├─ vector search (pgvector HNSW) ─┐
  ├─ keyword search (Postgres FTS) ─┴─ RRF fusion + policy/pricing boosts   (unchanged)
  │
  ├─ R5.01 RE-RANK  ── top N candidates (default 12, recommended 10)
  │      ├─ language gate / Hinglish→English gloss of the question (reranker input only)
  │      ├─ cross-encoder scores each (question, title + chunk) pair  [ONNX, own thread pool]
  │      └─ rank-fusion of the old order and the cross-encoder order ("fuse" mode)
  │         chunks below the cut keep their original order beneath the candidates
  │
  ├─ per-document cap (RETRIEVAL_MAX_CHUNKS_PER_DOC, was hard-coded 2)      (unchanged logic)
  ├─ focus-term tie-break, min-score cut                                     (unchanged)
  └─ top 8 chunks → LLM
```

On **any** reranker problem (still loading, busy, timeout, error, load failure) the result is
byte-for-byte the pre-R5.01 ranking. Tests assert this for every failure type.

### 1. Reranker engine — [`reranker.py`](../core/app/engine/rag/reranker.py) (new)

- **Runtime:** ONNX Runtime on CPU with HF `tokenizers`, no PyTorch. Both were already in the image
  via pipecat / faster-whisper; they are now pinned explicitly in `requirements.txt`.
- **Pinned model:** HF revision `233902d2…`, int8 file. The sha256 of the loaded file is logged and
  shown in the status endpoint.
- **Never blocks the event loop:** inference runs on a dedicated bounded thread pool. ORT
  spin-waiting is disabled so an idle reranker does not burn the CPU the voice pipeline needs.
- **Hard limits:** a timeout (600 ms) and a concurrency cap (2 inferences × 2 threads per process).
  Past either, the call returns a non-ok status and retrieval keeps its RRF order. A timed-out job
  still releases its slot when the worker finishes.
- **Background loading:** at startup warm-up, or lazily on first use. A request never waits for a
  load; until the model is ready it is served RRF order (`not_ready`). A failed load is retried
  after a 60 s back-off (`unavailable` meanwhile).
- **Score cache:** LRU of (model, question, passage) → score, so the `knowledge_lookup` tool
  re-running the question the planner already scored costs 0 ms.
- **Pure, tested fusion:** `fuse` = base_weight/(k + old_rank) + ce_weight/(k + ce_rank). `replace` =
  cross-encoder order only (kept for A/B). Ranks are fused, not raw logits, because the logits are
  unbounded and uncalibrated.
- **Hinglish gloss** (`gloss_query`): a deterministic word list turns "corner aur premium mein
  charge ka farak kya hai" into "corner and premium in charge of difference what is" for the
  cross-encoder only. Search, prompt and logs keep the caller's words. Words that are also English
  (me, se, par) are glossed only when the question contains an unmistakably Hindi word, so English
  questions are never touched. The built-in list is general Hindi only; domain words go in a
  per-tenant glossary.

### 2. Retrieval hook — [`retrieval.py`](../core/app/engine/rag/retrieval.py)

- `_apply_rerank()` runs after RRF and the membership boosts, before the per-document cap.
- The cross-encoder reads **title + chunk**: a cost-sheet row often only names its configuration in
  the document title.
- Non-candidates are kept beneath the candidates. The first version dropped them, which silently
  broke the per-document cap's reach for breadth; the eval caught it and a regression test guards it.
- The per-document cap is now `RETRIEVAL_MAX_CHUNKS_PER_DOC`.
- Tenant glossary loader (`tenant.settings["rerank_glossary"]`), cached for 5 minutes; a DB error
  degrades to no glossary.
- `retrieve(..., rerank=None|True|False)` lets the debug endpoint and the eval force it per call.

### 3. Debuggability

| Where | What you see |
|---|---|
| `GET /knowledge/reranker` | loaded model, file path, sha256, load time, per-status counters, latency p50/p95/max, in-flight count |
| `POST /knowledge/search` with `"rerank": true/false` | same question with and without re-ranking: per chunk `base_rank`, `rerank_score`, `rerank_rank`; top level `rerank` = status, language, `ce_query` (the glossed question), ms, which chunks entered/left the window, whether the top-1 changed |
| Planner trace (`retrieval.rerank`) | the same diagnostics for every live turn |
| Logs | one `rag.rerank status=… ms=… entered=… top1=[…]` line per retrieval; `status=timeout / skipped_busy / not_ready` at WARNING; model load and failure lines |
| `RETRIEVAL_RERANK_DEBUG_LOG=true` | full before/after candidate table per retrieval |

### 4. Deployment — [`Dockerfile`](../core/Dockerfile), [`requirements.txt`](../core/requirements.txt)

The pinned model is baked into the image (`/opt/models/hf`) before `COPY . .`, so code changes do not
re-download it. The step soft-fails: a HuggingFace outage cannot block a deploy. A missing model
shows as `unavailable` and retrieval keeps RRF order.

### 5. Zero-cost retrieval eval — [`eval_retrieval.py`](../core/scripts/eval_retrieval.py), [`retrieval_qrels.py`](../core/scripts/retrieval_qrels.py) (new)

See section 03.

## 03 · How it was measured (without spending LLM credits)

### Retrieval-only eval

`scripts/eval_retrieval.py` runs the same `retrieve()` the planner runs on a cold turn, on the 50
frozen golden questions (plus their misspelt romanised variants = 70 scored queries, 8 escalation
queries excluded), once per **variant** (e.g. rerank off / on / cap 3), against the live Postgres KB.

- **No agent turn, no LLM judge.** The only paid call is one embedding per question, cached on disk
  after the first run. The first run cost under $0.001; every run since cost **$0**.
- **Labels (qrels):** hand-written evidence anchors per question, matched on chunk *content*, so they
  survive re-ingestion. If a document changes so an anchor matches nothing, the eval stops with
  "STALE LABELS" instead of mis-scoring.
- **Metrics:** Complete@8 (all evidence in the 8 chunks the model reads, the headline), Recall@8,
  Recall@3, Hit@1, MRR, rerank latency p50/p95, and a paired sign test vs the baseline so a
  difference is labelled signal or noise. It also prints a shortlist of question ids worth paying an
  end-to-end run for.

### End-to-end confirmation

`scripts/eval_rag_accuracy.py --ids <13 questions> --trials 1`, with the feature on: 13 agent turns
plus judge calls, compared against every past run of the same questions.

## 05 · Latency: did it increase?

### Cost of one rerank (CPU, 4-core container, 2 threads)

| Candidates | Alone | 2 at once | 4 at once |
|---|---|---|---|
| 12 | 536 ms, 2 of 6 timed out | 543 ms, 1 of 12 timed out | half skipped (busy) |
| **10** | **430 ms, 0 timeouts** | **452 ms, 0 timeouts** | half skipped (busy) |
| 8 | 288 ms, 0 timeouts | 367 ms, 0 timeouts | half skipped (busy) |

At 4 simultaneous calls the concurrency cap (2) skips half of them whatever the candidate count.
That is a CPU capacity limit, and the fix is more cores, not a longer timeout. Real callers rarely
hit the knowledge base within the same ~0.4 s window; the eval fires calls at the same instant.

### Caller-visible latency, by path

| Path | Added latency | Why |
|---|---|---|
| Normal answer turn (planner speculative retrieval) | **~0 ms** | retrieval runs in parallel with the ~1.3 s `understand()` LLM call; a ~430 ms rerank finishes first |
| `knowledge_lookup` tool turn | **+~430 ms** (max = timeout) | retrieval is serial on this path |
| `UNDERSTANDING_CONCURRENT_WITH_PROPOSE=true` (P4-1, off by default) | +~430 ms | retrieval becomes serial |
| After the classifier moves to Cerebras/Groq (~100 ms) | +~300 ms | the rerank would no longer be hidden |

### Event-loop impact (the loop that runs the turn and the voice audio)

| Reranks running | Loop delay p50 | p99 | max |
|---|---|---|---|
| 0 | 0.29 ms | 1.1 ms | 2.4 ms |
| 1 | 0.42 ms | 2.6 ms | 4.0 ms |
| 2 | 0.42 ms | 3.1 ms | 46 ms |

Negligible, except for one 46 ms spike at 2 concurrent reranks. Audio moves in 20 ms frames, so
this could cause a rare, small glitch under load.

### Why the paid end-to-end run was slower

Turn latency in that run was p50 5.0 s vs 3.2 s in past runs. It is **not explained by the rerank**:
all 13 turns took the normal answer path, where the rerank overlaps the LLM call. The traces point
to:

- **Cold start:** the first 4 turns (fired at once at a freshly recreated container) took 6.0–12.3 s;
  the other 9 took 4.1–6.3 s.
- **Colder OpenAI prompt cache:** ~6.0k cached planner tokens per turn vs ~7.4k before.
- **Different day, 13 turns vs 117:** OpenAI latency varies day to day.

Same model (gpt-4o planner) and the same prompt size (+~150 tokens from the third chunk per
document). The runs were not back-to-back, so this is a strong inference, not a controlled
measurement.

### Answer

On normal answer turns: **no added latency** that callers would notice. On tool turns: **+~430 ms**.
The CPU cost is real (~430 ms per knowledge question) and becomes visible once the LLM calls get
faster.

## 07 · How to enable, verify, roll back

Enable (in `.env`):

```
RETRIEVAL_RERANK_ENABLED=true
RETRIEVAL_MAX_CHUNKS_PER_DOC=3
RETRIEVAL_RERANK_CANDIDATES=10
```

Recreate core (a plain `restart` does not re-read `.env`):

```bash
docker compose up -d core
```

Verify:

```bash
# model loaded? counters, latency, sha256
curl -H "Authorization: Bearer <token>" http://localhost:8000/knowledge/reranker

# one question with and without re-ranking
curl -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
     -d '{"query": "corner aur premium mein charge ka farak kya hai", "rerank": true}' \
     http://localhost:8000/knowledge/search

# free retrieval A/B (no LLM cost)
docker compose run --rm core python scripts/eval_retrieval.py --spelling-variants

# one question in detail, chunk by chunk
docker compose run --rm core python scripts/eval_retrieval.py --ids HI020 --show

# unit tests
cd core && python -m pytest tests/test_reranker.py -q
```

Roll back: `RETRIEVAL_RERANK_ENABLED=false` and `RETRIEVAL_MAX_CHUNKS_PER_DOC=2`, then recreate core.

Paid end-to-end confirmation (when budget allows), full 50 questions with the significance test:

```bash
docker compose run --rm -e EVAL_BASE_URL=http://core:8000 core sh -c "pip install -q openpyxl && python scripts/eval_rag_accuracy.py --concurrency 2 --compare ../eval_results/rag_accuracy/20260925_061029"
```

Note: `eval_rag_accuracy.py` skips `--compare` when `--ids` is given.

## 09 · Known limits & follow-ups

- **Significance:** the retrieval gain is consistent but not yet significant (p ≈ 0.14), and the
  end-to-end gain rests on one trial of 13 questions. A full 50-question run is the proper proof.
- **CPU capacity:** at ~4 simultaneous knowledge turns per 4-core box, about half skip the rerank
  (safe fallback, lost gain). Size CPU before relying on it at scale.
- **Faster LLMs erase the hiding:** once the classifier is on Cerebras/Groq, the rerank adds ~300 ms
  per knowledge turn. Options then: GPU inference, a smaller/distilled model, or fewer candidates.
- **Gloss coverage:** the built-in word list is general Hindi. Domain words ("khel kood" → sports,
  "suvidha" → amenities) should be curated per tenant in `rerank_glossary`.
- **Misspelt Hinglish** ("kia", "hei", "milegaa") is read as English by the shared language
  detector in `responder.py`. With `RETRIEVAL_RERANK_LANGUAGES=all` this no longer matters for
  re-ranking, but it still affects reply-language detection. Separate small task.
- **Qrels are tied to this KB** (44 chunks, 16 documents). A new tenant or re-written documents
  need new labels; the eval flags stale ones automatically.
- **Biggest remaining accuracy lever is not retrieval:** 35 of 71 historical failures are the
  responder inventing facts (HI003, HG033, HI049, EN016, EN050). Tightening the responder's
  grounding rules is the next step toward 95%.
- **Retrieval-side next steps:** R5.05 (Hinglish keyword matching) and R5.06 / R5.09 (query
  rewriting) target the misses a reranker cannot reach (HI029 "khel kood", HG035, EN139).
