# pgvector HNSW Index — R5.02 Build Log

**Task (R5.02):** pgvector index upgrade: IVFFlat → HNSW for faster query-time similarity search.
Owner: Nikhil. Phase 5 / P1 / RAG. Estimated effort M (1 day). Estimated saving on the sheet: **−15 ms TTFA**.

**Status:** Complete. Implemented, unit-tested (30 new tests, full suite 72/72), migration exercised
against a real Postgres in every index state, benchmarked at 20,000 chunks, and verified on the live
knowledge base with real embeddings. Search tuning is **on by default**, with a one-line kill switch.

**Verdict in one line:** the index the task asks for already existed, so the −15 ms saving is not
available (measured: HNSW beats IVFFlat by 0.7 ms). But checking it found a serious bug: vector search
was silently dropping correct results. That is now fixed, with recall going from **0.64 → 0.995**
(large tenant) and **0.02 → 1.00** (small tenant) at scale, at a cost of about +1 ms.

---

## 00 · The task, as written

> HNSW (Hierarchical Navigable Small World) gives O(log n) ANN search vs IVFFlat's O(sqrt(n)). On a
> medium corpus (10k–100k chunks): HNSW query ~5–8 ms vs IVFFlat ~20–30 ms.
> `CREATE INDEX CONCURRENTLY ... USING hnsw (embedding vector_cosine_ops)` with m=16,
> ef_construction=64. Zero downtime with CONCURRENTLY.
>
> Location: DB migration (`knowledge_chunks` table). TTFA Δ: −15 ms. Accuracy Δ: —.

Taken literally, the acceptance criteria are:

1. `knowledge_chunks.embedding` is served by an HNSW index (`vector_cosine_ops`, m=16, ef_construction=64).
2. The change is applied with zero downtime.
3. Vector search gets about 15 ms faster.

## 01 · What we actually found

### Finding 1 — HNSW was already in place; there was never an IVFFlat index

Migration [`0004_knowledge_indexes.py`](../core/migrations/versions/0004_knowledge_indexes.py) already
creates `ix_chunks_embedding_hnsw ... USING hnsw (embedding vector_cosine_ops)`. The live database
confirms it (pgvector 0.8.6):

| Index | Method | Valid | Parameters |
|---|---|---|---|
| `ix_chunks_embedding_hnsw` | hnsw | yes | defaults = **m=16, ef_construction=64** (exactly what the task specifies) |

So criterion 1 was **already met** before this task started, and the "upgrade" had nothing to replace.

### Finding 2 — the latency estimate does not hold

At today's size (35–45 chunks) Postgres does not use any vector index at all: it scans the whole table
because that is cheaper, and the full vector query takes about 2 ms. Even at the corpus size the task
targets, a head-to-head measurement at 20,000 chunks gives **IVFFlat 5.31 ms vs HNSW 4.58 ms, a
−0.73 ms difference**, not −15 ms. The sheet's "IVFFlat ~20–30 ms" figure is not what pgvector does
on this hardware.

### Finding 3 — the real problem: vector search silently drops correct results

An HNSW scan does not find "the N nearest chunks that match the WHERE clause". It walks the graph,
collects the `hnsw.ef_search` (default **40**) nearest vectors across the **whole table, all tenants**,
and only **then** applies our filters (tenant, project, `status='ready'`, effective dates, doc_type).
Every candidate that belongs to another tenant is thrown away after the fact.

On a multi-tenant table, a tenant whose chunks are a small share of the table therefore gets a few
rows back, or none, for a question its documents answer. Nothing errors. The agent simply behaves
as if the knowledge base doesn't contain the answer ("I don't have that detail to hand").

This was hidden only because the table is still small enough that Postgres never uses the index.
It would start happening exactly when the corpus grows. Evidence:

- **On the dev DB, index forced on, no filter at all:** `LIMIT 32` returned **19 of 35 rows**.
- **At 20,000 chunks, pre-R5.02 settings:** see section 03. A large tenant got **63.5%** of the
  correct results and every query came back short. A tenant owning 1% of the table got **0.5 rows
  out of 32** on average.

### Finding 4 — prepared statements can pick the wrong plan for a tenant

The app's driver (asyncpg) prepares every statement. After 5 executions Postgres may switch a prepared
statement to a **generic plan**, one planned without knowing which tenant is being searched. The right
plan depends heavily on that: a small tenant is served fastest (and exactly) by its btree tenant index,
a large one by HNSW. Measured at 20k chunks, the generic-plan path cost the large tenant **63.9 ms**,
against **4.9 ms** with a plan made for the actual tenant.

## 02 · What we built

### 1. Query-time scan tuning — [`vector_index.py`](../core/app/engine/rag/vector_index.py) (new)

Before every vector search, one round trip sets these values **for the current transaction only**
(`set_config(..., is_local => true)`), so nothing can leak to another request on a pooled connection:

| Setting | Value | Why |
|---|---|---|
| `hnsw.iterative_scan` | `relaxed_order` | pgvector 0.8+: if the filters discard candidates, the scan resumes the graph walk until the LIMIT is filled. **This is the main fix for Finding 3.** |
| `hnsw.ef_search` | `max(100, pool)` | Candidate list size; never below the number of rows requested (32). |
| `hnsw.max_scan_tuples` | `20000` | Upper bound on work per query, for a filter that matches almost nothing. |
| `plan_cache_mode` | `force_custom_plan` | Re-plans with the real tenant ID (~0.3 ms), so each tenant gets the right index. **Fix for Finding 4.** |

- The server's pgvector version is read once per process. On pgvector < 0.8 the iterative settings are
  skipped with a logged reason instead of erroring.
- All values are range-checked before being sent, so the server can never reject them. A rejection
  would abort the caller's transaction on the hot path.

### 2. Reshaped vector query — [`retrieval.py`](../core/app/engine/rag/retrieval.py)

`VECTOR_SQL_TUNED` has the same filters, parameters and output columns as the original `VECTOR_SQL`.
The inner `ORDER BY distance LIMIT n` sits inside a `MATERIALIZED` CTE and the outer query re-sorts by
distance, because `relaxed_order` can emit rows slightly out of order and the RRF ranking downstream
depends on exact vector rank. The original query is kept untouched and is used whenever tuning is
switched off.

### 3. Migration 0015 — [`0015_hnsw_index_reconcile.py`](../core/migrations/versions/0015_hnsw_index_reconcile.py)

It ensures `knowledge_chunks.embedding` has **exactly one valid HNSW index** with the R5.02 parameters.
A pure, unit-tested function (`plan_index_migration`) reads the live catalog and decides:

| State found | Action |
|---|---|
| Valid HNSW, cosine, m=16 / ef_construction=64 | **No-op** (this is the dev DB) |
| IVFFlat index | Build HNSW `CONCURRENTLY` under a temporary name, then drop IVFFlat `CONCURRENTLY`, then rename |
| INVALID index (a failed `CREATE INDEX CONCURRENTLY`) | Rebuild as above |
| HNSW with other parameters or opclass | Rebuild as above |
| Correct index plus redundant extra vector indexes | Drop the extras `CONCURRENTLY` |

- **Zero downtime:** the new index is always built before an old one is dropped, so search always has an
  index to use. `CONCURRENTLY` runs inside Alembic's `autocommit_block`.
- **Safe to re-run:** a failure half-way leaves a state the next run's plan repairs.
- **Operator controls:**
  - `VECTOR_INDEX_MIGRATION=plan_only` logs the plan and SQL without running it (for a manual
    maintenance window on a very large table).
  - `VECTOR_INDEX_BUILD_MEM=2GB` raises build memory.
- **Downgrade** is intentionally a no-op: 0015 only repairs the index that 0004 owns.

### 4. Debuggability

| Where | What you see |
|---|---|
| Log line on **every** retrieval | `rag.vector tenant=… pool=32 returned=32 eligible=n/a db_ms=4.6 scan=[hnsw ef_search=100 iterative=relaxed_order max_tuples=20000 plan=force_custom_plan pgvector=0.8.6]` |
| Warning, only when it matters | `rag.vector.underfilled`: matching rows existed that the index scan did not return. When the vector search comes back short, a count of eligible rows (capped at 32, about 1 ms) tells "this tenant has few chunks" apart from "the index dropped rows". |
| Turn trace | `retrieval.vector` = `{vector_ms, pool, returned, scan, eligible, underfilled}` |
| `POST /knowledge/search` | the same `vector` block in the response |
| Deep dive | `RETRIEVAL_VECTOR_EXPLAIN=true` logs `EXPLAIN (ANALYZE, BUFFERS)` of each vector query (debug only; runs it twice) |
| On demand | [`scripts/vector_index_report.py`](../core/scripts/vector_index_report.py): index state, migration plan, live recall/latency, forced-index comparison, synthetic scale benchmark. It runs in one transaction that is always rolled back. |

### 5. Configuration — [`config.py`](../core/app/config.py), `.env.example`

| Env var | Default | Purpose |
|---|---|---|
| `RETRIEVAL_HNSW_TUNING_ENABLED` | `true` | **Kill switch.** `false` = exact pre-R5.02 query path, no redeploy |
| `RETRIEVAL_HNSW_EF_SEARCH` | `100` | Validated 1–1000 |
| `RETRIEVAL_HNSW_ITERATIVE_SCAN` | `relaxed_order` | `relaxed_order` / `strict_order` / `off` |
| `RETRIEVAL_HNSW_MAX_SCAN_TUPLES` | `20000` | Work cap per scan |
| `RETRIEVAL_VECTOR_FORCE_CUSTOM_PLAN` | `true` | Per-tenant planning |
| `RETRIEVAL_VECTOR_UNDERFILL_CHECK` | `true` | The underfilled diagnostic |
| `RETRIEVAL_VECTOR_EXPLAIN` | `false` | Debug only |
| `VECTOR_INDEX_MIGRATION` | `auto` | `plan_only` to defer the index build |

## 03 · What we checked

### Check 1 — scale benchmark: 20,000 chunks × 1536 dims, 20 tenants

This was run with `vector_index_report.py --synthetic 20000`, using the production SQL against TEMP
tables (real tables untouched). The layout is one small tenant (1% of rows), one large tenant (50%),
and the rest spread evenly, all in a shared semantic space. Each group had 30 queries and asked for
pool = 32 rows. Recall is measured against an exact scan.

**Large tenant (10,000 chunks)**

| Mode | p50 ms | p95 ms | Recall | Short queries |
|---|---:|---:|---:|---:|
| Exact scan, no index | 109.22 | 142.14 | 1.000 | 0/30 |
| IVFFlat (probes=1) | 5.31 | 6.96 | 1.000 | 0/30 |
| **HNSW, pre-R5.02 defaults** | 3.87 | 5.02 | **0.635** | **30/30** |
| HNSW, R5.02 settings (index forced) | 4.58 | 6.04 | 0.995 | 0/30 |
| Generic plan (what caching can fall into) | 63.86 | 71.63 | 1.000 | 0/30 |
| **Production path after R5.02** | **4.90** | 5.94 | **0.995** | **0/30** |

**Small tenant (200 chunks = 1% of table)**

| Mode | p50 ms | p95 ms | Recall | Avg rows returned |
|---|---:|---:|---:|---:|
| Exact scan, no index | 7.49 | 9.17 | 1.000 | 32.0 |
| IVFFlat (probes=1) | 4.38 | 5.75 | 0.156 | 10.4 |
| **HNSW, pre-R5.02 defaults** | 2.22 | 3.00 | **0.016** | **0.5** |
| HNSW, R5.02 settings (index forced) | 33.98 | 44.16 | 0.955 | 32.0 |
| **Production path after R5.02** | **2.93** | 3.86 | **1.000** | **32.0** |

How to read this:

- **Before R5.02**, the large tenant lost a third of its correct results on every query, and the small
  tenant got almost nothing back. This is the silent failure from Finding 3.
- **After R5.02**, the production path returns the right rows for both tenants (0.995 / 1.000) in
  about 3–5 ms.
- Forcing HNSW for a tiny tenant is slow (34 ms): the scan has to walk most of the graph to find 1% of
  the rows. `force_custom_plan` is what keeps production away from that. The planner sends the small
  tenant to its btree index (2.9 ms, exact) and the large tenant to HNSW.
- Build cost at 20k: HNSW 14.9 s vs IVFFlat 2.1 s, both about 156 MB. That is a one-time cost, and
  with `CONCURRENTLY` it doesn't block reads or writes.

### Check 2 — live knowledge base (45 real chunks, real embeddings)

| Mode | p50 ms | Recall | Short |
|---|---:|---:|---:|
| Exact scan | 1.85 | 1.000 | 0/30 |
| Production path after R5.02 | 2.12 | 1.000 | 0/30 |
| Forced IVFFlat / HNSW default / HNSW R5.02 (on a temp copy) | 2.12 / 2.23 / 2.11 | 1.000 | 0/30 |

At 45 chunks Postgres scans the table directly and every mode is equivalent. R5.02 costs about nothing
at today's size.

End-to-end through the real `retrieve()` with real OpenAI embeddings: "what is the price of a 3 bhk",
"is there a daycare at the clubhouse" and "do you have a generator" all returned the full 32 vector
results with no errors, and the diagnostics block populated correctly. Vector search took 3.5–4.6 ms
once warm (the first call in a process was 28 ms, because it includes the one-time pgvector version
check).

### Check 3 — migration 0015 on a real Postgres, every index state

This ran against a throwaway database with 2,000 real 1536-d vectors, through the actual Alembic runner:

| Scenario | Result |
|---|---|
| State as 0004 leaves it | `plan=noop` |
| Index replaced by IVFFlat | HNSW built `CONCURRENTLY`, IVFFlat dropped, renamed; final index valid with `m=16, ef_construction=64` |
| Index marked INVALID | Rebuilt; final index valid |
| `VECTOR_INDEX_MIGRATION=plan_only` with an extra IVFFlat | SQL logged, **nothing changed** |
| Re-run in `auto`, then again | Extra index dropped, then `plan=noop` |
| Dev database | `plan=noop`, now at `0015 (head)` |

### Check 4 — transaction safety

After a retrieval, the settings are visible inside the transaction (`ef_search=100`,
`force_custom_plan`). After the transaction ends they are back to server defaults (`ef_search=40`,
`auto`), so nothing leaks between requests.

### Check 5 — tests

| Suite | Result |
|---|---|
| [`tests/test_vector_index.py`](../core/tests/test_vector_index.py) (new) | **30 passed** |
| Full suite (`core/tests`, excluding `bench/` and `test_ttfa_wire.py`, which needs `pipecat` locally) | **72 passed** |
| `python -m app.engine.rag.retrieval` selftest | PASS |

The new tests cover:

- **Migration planner:** every index state; build before drop; `CONCURRENTLY` everywhere; leftover cleanup.
- **Scan configuration:** `ef_search` at least the pool size and clamped; old pgvector degrades
  gracefully; the kill switch; the custom-plan flag.
- **Settings application:** every value is transaction-scoped; the version is cached; nothing runs when
  tuning is disabled.
- **Vector search:** the tuned SQL is used, and the original SQL when switched off; underfilled is
  flagged only when more eligible rows exist; a failing diagnostic never fails the search; the tuned
  SQL keeps every filter.

The existing suite caught one fragile line in the planner trace (a test double without the new method).
It was made defensive rather than changing the tests.

## 05 · Why the task is considered complete

1. **The deliverable the task names exists and is guaranteed.** `knowledge_chunks.embedding` has
   exactly one valid HNSW cosine index with m=16 / ef_construction=64. Migration 0015 enforces it and
   repairs drift in any environment (IVFFlat, invalid, wrong parameters, duplicates) with zero downtime.
   This is verified on a real database for every one of those states.
2. **The latency target was checked, not skipped.** The −15 ms rested on two premises: that the index
   was IVFFlat, and that IVFFlat costs 20–30 ms. The first is false, and we measured the second at the
   task's own target scale (20k chunks: 5.3 ms vs 4.6 ms). No further work on this index can recover a
   15 ms saving that isn't there. Keeping the task open would not move TTFA.
3. **The goal behind the task, fast and correct vector search at scale, is now met.** The investigation
   exposed a failure mode that would have hit production as the corpus grew: the agent denying facts
   that are in its documents. It is fixed at a cost of about 1 ms, stays off the hot path's error
   surface, and has a kill switch.
4. **It is production-grade and debuggable.** Every setting is transaction-scoped; old pgvector
   degrades gracefully; the diagnostics can never fail a turn. There is a log line on every retrieval,
   a warning when results are dropped, trace and API fields, and a report script that measures all of
   it on demand.
5. **Tested at every layer:** 30 new unit tests and the full suite green, migration runs on a real
   Postgres, a scale benchmark, and an end-to-end retrieval on live data with real embeddings.

## 08 · Known limits & follow-ups

- **Benchmark data is synthetic at scale.** The live corpus is 45 chunks, so the at-scale numbers come
  from clustered synthetic vectors, which are harder for HNSW than real embeddings. Re-run
  `--mirror` once a real tenant passes about 5k chunks.
- **A very small tenant with the index forced is slow (34 ms).** Production avoids this through
  per-tenant planning. If `RETRIEVAL_VECTOR_FORCE_CUSTOM_PLAN` is ever turned off, watch
  `rag.vector` `db_ms` for small tenants.
- **Fresh databases lack 22 server-side DEFAULTs** (e.g. `is_active`, `metadata`, `status`), because
  the models only set Python-side defaults. The app is unaffected, but raw-SQL inserts that omit those
  columns fail on a new environment. The fix is to add matching `server_default`s to the models.
- **Ranking, not recall:** "what is the price of a 3 BHK" puts the pricing-policy document above the
  3 BHK cost sheet. That's a re-ranking issue, a natural first test case for **R5.01** (cross-encoder
  re-ranking).
