# Parallel Preconditions — P2.05 Build Log

**Task (P2.05):** Run the tool executor's precondition DB queries in parallel instead of
sequentially. Owner: Nikhil. Estimated saving: −35 ms on tool turns.

**Status:** Implemented, tested (12 unit tests), validated on live calls. Ships behind a
feature flag, default **off**.

**Scope note:** the change lives entirely in the shared tool executor, so it applies to
**both inbound and outbound** calls — every tool on either path runs through the one
`execute()` entry point; direction is only a field in `ctx.extra["direction"]`, never a
separate code path.

---

## 00 · The task, as written

> Preconditions runs 2–3 DB SELECTs sequentially (slot availability, customer lookup, centre
> lookup). Use `asyncio.gather()` to run them in parallel. DB allows concurrent connections.
> Saves: (N_queries − 1) × 15 ms RTT ≈ 30 ms for 3 queries.
>
> File: `core/app/engine/tools/executor.py` — preconditions.

---

## 01 · What the code actually did, and the hazard the sheet got wrong

The executor evaluates a tool's preconditions in a plain sequential loop
([`core/app/engine/tools/executor.py`](../core/app/engine/tools/executor.py)):

```python
for spec in (tool.preconditions or []):
    res = await contracts.run_check(name, ctx, args)   # each awaited fully before the next
    ...
```

For `book_appointment` — the tool with the most preconditions — that is four DB checks run
back-to-back (`centre_exists`, `executive_exists`, `slot_available`, `no_conflicting_appointment`),
plus two in-memory ones. Their times **add up**.

**The trap in the sheet's one-liner:** *"DB allows concurrent connections"* is true but is not
the constraint. Every check shares **one** `AsyncSession` (`ctx.db`), and a SQLAlchemy
`AsyncSession` is **not safe for concurrent use** — it multiplexes onto a single connection.
A naive `asyncio.gather()` of checks that each `await ctx.db.execute()` on that shared session
raises `InvalidRequestError: ... concurrent operations are not permitted`. So the naive
approach *crashes* on exactly the booking turns it is meant to speed up.

Real parallelism therefore requires **each concurrent DB check to run on its own
session/connection**. That is the core of what was built.

## 02 · What we built

### 1. A precondition runner with two paths — `[executor.py](../core/app/engine/tools/executor.py)`

`_run_preconditions()` replaces the inline loop and returns the check trace **in declared
order**, so the caller still blocks on the first not-ok check exactly as before.

- **Sequential path** (`_preconditions_sequential`): the original loop on the shared session,
  short-circuiting on first failure. This is what runs with the flag off, and the fallback if
  the parallel path ever errors — byte-for-byte the pre-P2.05 behaviour.
- **Parallel path** (`_preconditions_parallel`): in-memory checks run inline; DB checks run
  concurrently, **each on its own short-lived, read-only `AsyncSession`** (own pool
  connection), gathered with `return_exceptions=True`. Results are reassembled in declared
  order, so "first failing check wins" is deterministic and the outcome is identical to
  sequential.

### 2. In-memory vs DB check classification — `[contracts.py](../core/app/engine/tools/contracts.py)`

`IN_MEMORY_CHECKS` / `is_in_memory_check()` mark the checks that touch no database
(`customer_identified`, `identity_verified`, `slot_was_offered`). Those run inline in
microseconds — opening a side connection for them would be pure waste. Misclassification here
can only ever cost performance, never correctness.

### 3. Bounded concurrency (pool protection) — `config.py` + `executor.py`

A per-event-loop semaphore caps how many precondition side-connections may be open at once
across all in-flight turns (`parallel_preconditions_max_concurrency`, default 8), so a burst of
simultaneous booking turns cannot exhaust the Postgres pool.

### 4. The uncommitted-write safety gate — `executor.py`

Side sessions read on **separate connections** and therefore see only **committed** data. If an
earlier tool in the same turn's chain flushed an uncommitted write, a later precondition on a
side connection could miss it (e.g. a freshly-booked appointment that a following
`no_conflicting_appointment` should see). To prevent that, `_record()` sets a
`_pending_tool_write` flag on the session (cleared automatically on the turn's commit via a
SQLAlchemy `after_commit`/`after_rollback` listener); while it is set, `_run_preconditions`
falls back to the sequential shared-session path. The common single-tool turn — where
preconditions run *before* any tool write — always parallelises.

### 5. Debuggability — `executor.py`

- Per-check wall-time (`ms`) is folded into `outcome.validation["checks"]`, so it persists on
  the `tool_execution` audit row and can be queried after the fact.
- With `parallel_preconditions_trace` on, one structured log line per turn reports which checks
  ran in parallel vs inline, each check's time, and the sequential-sum vs actual-wall saving:

  ```
  preconditions[parallel] tool=book_appointment checks=6 wall=30.7ms seq_sum=59.2ms saved=28.5ms
  detail={'customer_identified':0.0,'slot_was_offered':0.0,'centre_exists':14.4,
          'executive_exists':2.9,'slot_available':29.1,'no_conflicting_appointment':12.8}
  ```

### 6. Warm connection pool (the finding-driven follow-on) — `[base.py](../core/app/db/base.py)` + `[main.py](../core/app/main.py)`

Live testing (see §04) showed the parallel fan-out paying a cold-connection tax. The fix:

- **Explicit, tunable pool** on the async engine (`db_pool_size=10`, `db_max_overflow=20`)
  instead of SQLAlchemy's tiny 5/10 default.
- **Concurrent startup warming** — `warm_pool(n)` opens `n` connections *at the same instant*
  (an `asyncio.Barrier` holds them all open together) so the pool retains that many **warm**
  connections. Opening them one-at-a-time does not work: the pool hands back the same single
  connection each time and warms nothing. Driven by `db_warm_connections=4`, called from the
  existing best-effort startup warm-up (P1.08).

## 03 · Why it's safe (the correctness argument)

1. **Preconditions are read-only and order-independent** — no check mutates `ctx`; only
   postconditions use `$result`. Running them concurrently or out of order changes nothing
   functionally.
2. **The reported blocker is deterministic** — results are reassembled in declared order and
   the caller blocks on the first not-ok check, identical to the sequential loop.
3. **Uncommitted intra-turn writes are handled** — the pending-write gate (§02.4) keeps any
   tool that could depend on an earlier tool's uncommitted write on the shared session.
4. **Postconditions are intentionally NOT parallelised** — a postcondition reads the tool's own
   just-written (uncommitted) rows (e.g. `row_exists` after `create_customer`). A side
   connection cannot see an uncommitted INSERT, so postconditions must stay on the shared
   session. This is a hard correctness boundary, not an oversight.
5. **Degrades safely** — any infrastructure failure in the parallel path (pool timeout,
   connection drop) falls back to the proven sequential path; it can never fail a turn the old
   loop would have passed.
6. **Flag off = no change** — with `parallel_preconditions_enabled=false`, execution is the
   original sequential loop.

## 04 · Findings from live calls

### Finding 1 — the parallel path works, and hit the −35 ms target immediately

First live booking turn (cold pool, before warming):

```
book_appointment checks=6 wall=147.3ms seq_sum=181.2ms saved=33.9ms
```

−33.9 ms, essentially the sheet's −35 ms estimate — on a real inbound booking.

### Finding 2 — a cold-connection spike was capping the win

The same trace's detail exposed an outlier:

```
centre_exists:10.0  executive_exists:4.4  slot_available:21.2  no_conflicting_appointment:145.6
```

`no_conflicting_appointment` took **145 ms** vs an ~18 ms benchmark. It was **not** a slow
query — the `ix_appt_customer` index on `(tenant_id, customer_id)` exists and a customer has few
rows. The tell: the other three concurrent checks were fast (4–21 ms), and a single earlier
`search_slots` side-session was 9.9 ms. Only the check that had to **build a fresh TLS
connection** to the remote (Railway) Postgres was slow. **The parallel fan-out needs several
connections at once; with only one warm, the extras are created cold.**

### Finding 3 — warming the pool removed the spike

After adding concurrent startup warming and an explicit pool, the same booking turn:

```
book_appointment checks=6 wall=30.7ms seq_sum=59.2ms saved=28.5ms
detail={... centre_exists:14.4, executive_exists:2.9, slot_available:29.1,
        no_conflicting_appointment:12.8}
```

`no_conflicting_appointment`: **145.6 ms → 12.8 ms**. Precondition wall-time:
**147 ms → 31 ms (~5×)**. And `wall (30.7) ≈ slowest check (slot_available 29.1)` — i.e. *ideal*
parallelism: the stage now costs about what its single slowest check costs.

### Finding 4 — an event-loop stall on `create_customer` is NOT from this work

Traces showed a ~130–147 ms `event-loop stalled` warning on `create_customer` turns. It was
**ruled out** as P2.05-related:

- It **reproduces with the flag off** (control run).
- `create_customer` has **zero preconditions** (only a postcondition), so the parallel path
  never engages for it.
- `warm_pool` runs only at startup, not per turn.
- The `Task@create_customer:62` shown by the monitor is *awaiting* a DB SELECT (a bystander),
  not the CPU-bound blocker; the loop monitor lists all in-flight tasks.

Most likely cause: first-use SQLAlchemy statement-compile on the write path (Customer INSERT,
Conversation update, audit INSERT, `row_exists` postcondition), which the P1.08 warm-up does not
prime. Tracked as a **separate** P1.08 follow-up, not part of P2.05.

## 05 · Enabled vs disabled — the comparison

The trace's `seq_sum` (sum of the checks = the sequential/disabled equivalent) vs `wall`
(parallel actual), same warm-pool conditions, `book_appointment`:

| mode | precondition wall-time | how |
| :---- | ----: | :---- |
| Disabled (sequential) | ~59 ms | 14.4 + 2.9 + 29.1 + 12.8 (checks add up) |
| Enabled (parallel) | ~31 ms | ≈ slowest check (slot_available 29.1) |
| **Difference** | **−28 ms (~48%)** | sequential pays the sum; parallel pays the max |

**Mechanism:** the more DB preconditions a tool has, the larger the gap. Benefit by tool:

| tool | DB preconditions | benefit |
| :---- | ----: | :---- |
| `book_appointment` | 4 | large (−28 ms measured) |
| `reschedule_appointment` | 2 | moderate |
| `cancel_appointment` | 2 | moderate |
| `search_slots` | 1 | none (nothing to overlap) |
| all others | 0–1 | none (no behaviour change) |

**Honest caveats:**

- `seq_sum` slightly *over*-states true disabled cost: in parallel mode each check pays its own
  connection checkout + one `pool_pre_ping` round-trip, whereas true sequential reuses the one
  already-open call connection. So read ~48% as "close to 2×," not exact.
- This is one pipeline stage. ~28 ms off a booking turn is on-target for P2.05 but a slice of
  the ~1,560 ms TTFA budget; its value compounds with the other P2/P3 levers.

## 06 · Configuration & rollout

All flags in [`core/app/config.py`](../core/app/config.py). Defaults are safe (feature off);
enabling is a `.env` change, no code change.

| Setting | Default | Purpose |
| :---- | :---- | :---- |
| `parallel_preconditions_enabled` | `false` | Master switch. Off = original sequential behaviour. |
| `parallel_preconditions_max_concurrency` | `8` | Cap on concurrent precondition connections (pool protection). |
| `parallel_preconditions_trace` | `false` | Per-turn structured timing log. |
| `db_pool_size` | `10` | Explicit async pool size (holds warm connections). |
| `db_max_overflow` | `20` | Burst headroom above pool_size. |
| `db_warm_connections` | `4` | Connections primed concurrently at startup. |

**Recommended rollout:**

1. `DB_WARM_CONNECTIONS=4` and pool settings are safe to ship on immediately (they only warm
   and size the pool; no behaviour change).
2. Enable `PARALLEL_PRECONDITIONS_ENABLED=true` per environment, with
   `PARALLEL_PRECONDITIONS_TRACE=true` during validation.
3. Watch the startup line `warm-up: DB pool primed (4 connection(s)) + ORM cache` and the
   `preconditions[parallel] ... saved=` lines on booking turns.

**Pool sizing note:** total server connections ≈ `replicas × (db_pool_size + db_max_overflow)`.
Keep under the Postgres `max_connections` budget (managed Postgres is often ~100). Lower the
defaults for many replicas or a small DB plan.

## 09 · Known limits & follow-ups

- **Per-check RTT floor.** Even fully warm, each side-session checkout pays ~1 network
  round-trip for `pool_pre_ping`'s liveness `SELECT 1` (~15 ms to a remote DB). That is why the
  "fast" checks sit at 10–21 ms. Warming removes the *spikes*, not the floor.
- **Only 2+-DB-precondition tools benefit** (`book_appointment`, `reschedule_appointment`,
  `cancel_appointment`). This is expected, not a gap.
- **Sequential-mode tracing.** The `preconditions[parallel]` line prints only in parallel mode.
  A direct in-log A/B in *both* modes would need a small addition to the sequential path (behind
  the same trace flag) — not yet done.
- **`create_customer` event-loop stall** (§04, Finding 4) — separate P1.08 warm-up follow-up.
- **Co-locating the app in Mumbai (P2.07)** would cut the RTT floor above for every check.
