## 00 · The task, as written

From the task sheet: *"Chunk metadata enrichment at ingestion: extract price points, BHK types."*
Files `core/app/engine/rag/ingestion.py + chunkers.py`, effort M (2d), target **TTFA −5 ms,
accuracy +5%**.

The note said: run lightweight regex extraction on each chunk — price patterns (₹X lakh, X crore,
Rs X), BHK configurations (1 BHK, 2.5 BHK), area ranges (X sq ft) — store them as chunk metadata,
and enable pre-filter retrieval (*pricing query → only search chunks with price metadata*), which
"reduces retrieval pool size → −5 ms + +5% precision".

---

## 01 · The problem we were solving

Chunks carried only `heading`, `doc_type`, `title` and `kind`. Retrieval had no idea *what facts a
chunk states*, so it could only guess from words and document type:

1. **Price questions were judged per document, not per chunk.** `PRICING_BOOST` lifted every chunk
   of a `doc_type='pricing'` document — including ones that state no number — and gave nothing to a
   brochure or policy chunk that quotes a price. A tenant who never tags `doc_type` gets nothing.
2. **Hinglish price questions were invisible.** `PRICING_MARKERS` is English-only: "clubhouse ka
   charge kitna hai" and "corner aur premium mein charge ka farak" triggered no pricing lift.
3. **BHK matching was a substring check**, unable to say which configurations a cost-sheet row
   covers — the task sheet's own example is a 3 BHK sheet ranking above the 2.5 BHK rows.
4. **No visibility** into why a chunk made the window.

---

## 02 · The journey, step by step

### 1. Read the real documents first — the task note's formats were not the real ones
The seeded cost sheets almost never write "₹X lakh". They write **bare Indian-grouped numbers
behind a label**: `Flat cost 96,25,000. Total 1,03,93,750.`, `Clubhouse charges 3,25,000`,
`Carpet 592`, `Rate 11,000 rupees per square foot`. The same text is full of numbers that are *not*
prices: `Balcony and utility 99`, `sr3`, `4th floor`, `1 June 2026`, phone numbers. An extractor
that only matched ₹/Rs would have tagged almost no real price row.

### 2. Found and fixed a pre-existing chunker bug that was corrupting data
While validating extraction, the "Unit Mix by Tower" chunk came out as areas `[422, 390]`. Cause:
`chunkers.py` split inline comma-lists on **every** comma, including digit-group commas. The stored
chunk read `"3 BHK of 1, 422 and 1, 390 sq ft"`, and the trailing `1,104` fragment fell under
`min_chars` and was **silently dropped**. The agent had been reading corrupted areas. Fixed with a
separator that ignores a comma between two digits; only that one seed document was affected, and it
was re-ingested.

### 3. Built the extractor, ingestion tagging, retrieval boost/filter and debug surface
See §04. Default mode **boost** (not the task's hard filter — see §05 for why).

### 4. Measured, and let the measurements find the bugs
Four eval stages plus a paired retrieval A/B (§03). Each regression the evals surfaced was traced to
a query-analyser misreading and fixed with a test:

| Found by | Question | Misread as | Fix |
|---|---|---|---|
| Accuracy eval | "How many flats **in total**?" (EN027) | price | "total" dropped as a price cue; count guard ("how many", "kitne flats") |
| Retrieval probe | "…**per square feet** kitna padta hai" (HI010) | size | rate units stripped before the area check |
| Retrieval A/B | "Where can I verify the RERA **registration**?" | price | bare "registration" dropped as a price cue |
| Retrieval A/B | "**common area** maintenance charges" | size | "common/play/parking … area" stripped before the area check |

Plus a coverage pass over all 50 golden questions, which fixed missed cues: "ballpark", "floor rise
**charged**", "1390 sq ft ka kitna **banta** hai", "**ek** BHK", "2 **and** 3 bedroom".

### 5. Established how noisy the measurements are
Before trusting any delta, we measured noise directly (§03). Both instruments turned out to be
noisier than the effect we were measuring — which is the central caveat of this report.

## 03 · Test results

### 3.1 End-to-end answer accuracy — `scripts/eval_rag_accuracy.py` (50 golden questions, 2 trials)

| Stage | What changed | Accuracy | vs A |
|---|---|---|---|
| Original baseline | — (1 trial) | 86.0% (43/50) | — |
| **A** re-baseline | nothing (chunks untagged ⇒ boost is a no-op) | **88.0%** (44/50) | — |
| B | R5.08 boost on, tags backfilled | 86.0% | −2 pts, p=1.0 |
| B2 | + query-analyser fixes | 86.0% | −2 pts, p=1.0 |
| **C** | + chunker fix (Unit Mix re-ingested) | **88.0%** (44/50) | **0 pts**, p=1.0 |

- **No significant change.** Stage A — an unchanged system — itself moved +2 pts from the original
  86%, so ±1 question is noise. 4 questions flip between trials of the same build.
- The golden set's remaining failures are **generation**, not retrieval: a missing "GST/registration
  not included" caveat (HI003), forbidden claims about pets and corpus-fund refunds (HG033, EN016),
  a clarifying question instead of an answer (HI052). Ranking cannot fix these.
- HI020 ("corner vs premium charge") stays a retrieval miss for a reason outside R5.08:
  `MAX_CHUNKS_PER_DOC=2` admits only two chunks of the charges document, and the "premium 75 rupees"
  chunk loses that slot.

### 3.2 Retrieval precision — `scripts/eval_metadata_ab.py` (paired off vs boost, RAGAS judge)

Paired design: each question is retrieved in both modes in one process from the **same cached
embedding**; only questions whose window differs are judged.

| Run | Judge | Questions judged | Precision off → boost | Δ |
|---|---|---|---|---|
| 1 | gpt-oss-20b | 4 (daily cap hit) | 0.78 → 0.91 | +12.5 pts — too small to use |
| 2 | gpt-oss-120b | 10 of 13 (daily cap hit) | 0.854 → 0.893 | **+3.9 pts** (+4.6% rel) — includes CAM bug |
| 3 | gpt-oss-120b | 8 of 8, after CAM fix | 0.911 → 0.921 | **+0.9 pts** (+1.0% rel) — cleanest |

- **Recall: 1.00 → 1.00 on every judged question.** R5.08 never displaced a needed chunk.
- **The judge is noisy.** On *identical* windows, run 2 scored "base flat cost 1560 sq ft" 0.62→1.00
  and run 3 scored it 0.62→0.70; "all-inclusive price, smallest 3BHK" scored 0.50 then 1.00 for the
  same off-mode window. Per-question judge variance (0.3–0.5) is larger than the effect.
- **Best estimate: ~+2.5 pts (~+3% relative) precision on affected questions, ~+1 pt overall** —
  directionally positive, not statistically established.

### 3.3 Reach — which questions R5.08 touches (A/B, 42 answerable questions)

- Window **changed on 14/42 (33%)** — all price, size or BHK questions, as intended (Q1–8 prices and
  charges, Q14–18 sizes and configurations). 27 were identical (amenities, specs, location, builder).
- One unintended change (RERA registration) was the bug fixed in §02.

### 3.4 Latency

| A/B run | off p50 | boost p50 | Δ |
|---|---|---|---|
| 1 (`--no-judge`, 42 q) | 11.68 ms | 11.90 ms | +0.22 ms |
| 2 (18 q) | 9.24 ms | 9.45 ms | +0.21 ms |
| 3 (8 q) | 9.52 ms | 9.79 ms | +0.27 ms |

Warm retrieval with the embedding cached, i.e. DB + ranking. **~+0.2 ms (+2%)**, consistently.
Micro-benchmarked cause (the SQL is identical in both modes):

| Extra work in boost mode | Cost |
|---|---|
| `analyze_query` (~a dozen regexes) | 0.05–0.11 ms |
| `apply_metadata_boosts` over ~32 candidates | 0.02–0.07 ms |
| `rag.meta` INFO log line | ~0.02 ms (more via Docker stdout) |

≈0.01% of a ~1,500 ms turn — not worth optimising. If ever needed: cache `analyze_query` per query
string, and log `rag.meta` at DEBUG.

## 04 · What we built

**Extractor — `app/engine/rag/enrichment.py` (new, stdlib-only).** Rules run most-specific first and
each *claims* its span so a looser rule can never re-read the same digits:

1. BHK (`2.5 BHK`, `3bhk`, `1, 2 and 3 BHK`, `ek BHK`, `three bedroom`) → never money
2. rate (`11,000 rupees per square foot`, `₹11,499/sq ft`, `250 per sq ft`)
3. area with unit, incl. lists (`619, 625, 643 and 646 sq ft`)
4. area by label (`Carpet 592`, `super built-up 1,325`)
5. money with currency/scale (`₹60L`, `Rs.3,25,000`, `5.5 lakh`, `1.54 crore`, `80 लाख`)
6. money by cost-sheet label (`Total 1,03,93,750`, `Car parking is 3,00,000`), only if ≥ 1,000
7. a bare Indian-grouped figure ≥ 1,00,000

Stored as `metadata.facts = {v, has_price, has_rate, has_area, bhk, prices, rates, areas,
*_min, *_max}`; lists capped at 24 values, min/max over all. `FACTS_VERSION = 2`.

**Query analyser — `analyze_query()`** returns `{price, rate, area, bhk, budget}` intent, English and
romanised Hindi, with guards for count, distance, size-vs-price "kitna", rate units and named areas.

**Ingestion — `ingestion.py`.** Tags every chunk from `embed_text` (heading + body — the same text
stored as `content`, so backfill reproduces it exactly). A tagging failure stores the chunk untagged
and logs `rag.enrich failed`; it can never fail an ingest. Per-document `rag.enrich` coverage log;
coverage counts returned by the ingest/re-ingest APIs.

**Retrieval — `retrieval.py`.** `RETRIEVAL_METADATA_MODE`:
- `off` — kill switch; analysis skipped, ranking identical to pre-R5.08.
- `boost` (default) — **membership** lifts before the base-score snapshot: price ×1.3 (skipped for
  chunks already given the document-level `PRICING_BOOST`, so nothing double-counts), area ×1.2,
  exact-BHK ×1.2; combined lift capped at **1.6** (parity with `PRICING_BOOST`). Untagged chunks are
  neutral.
- `filter` — boost **plus** the vector arm restricted to chunks carrying the fact. Untagged chunks
  stay eligible; the keyword arm stays unfiltered as a safety net; if the filtered pool is smaller
  than `top_k`, the vector search re-runs unfiltered (`filter_fallback` in diagnostics).

**Chunker fix — `chunkers.py`.** `_split_items` never splits on a comma between two digits.

**Debuggability.**
- `rag.meta` log line per retrieval with intent (mode, intent, tagged/untagged, lifts per type,
  lifted chunks that reached the window, filter, fallback); DEBUG for no-intent queries.
- `rag.meta.untagged` warning when no candidate chunk is tagged (backfill not run).
- `RetrievalResult.metadata` → planner turn trace (`retrieval.metadata`) and `/knowledge/search`,
  which also shows each chunk's `facts` and `meta_boosts`. Facts are **not** added to the prompt.

**Scripts.**
- `scripts/backfill_chunk_metadata.py` — tags existing chunks from stored content, **no
  re-embedding, no cost**. Dry-run by default, `--apply`, idempotent (only untagged / older-version
  chunks), jsonb-merges only `facts`, one transaction per tenant, per-document coverage report that
  flags a pricing document with no priced chunk.
- `scripts/eval_metadata_ab.py` — the paired A/B above: `--mode-b boost|filter`, `--no-judge`,
  `--judge openai|groq`, `--judge-model`, `--judge-tpm` (client-side token pacing for rate-limited
  judges), `--concurrency`, `--limit`. Judge failures are excluded from the mean, not counted as 0.

## 05 · What we built vs the task sheet

| Task sheet said | What we did | Why |
|---|---|---|
| Regex for "₹X lakh, X crore, Rs X" | 7 ordered rules incl. label-anchored and Indian-grouped bare numbers | Real cost sheets write `Total 1,03,93,750` — the sheet's formats would have missed nearly every row |
| Pre-filter: pricing query → only price chunks | `boost` default; `filter` opt-in, vector-arm only, with fallback | A hard filter hides valid no-number answers ("there is no 1 BHK cost sheet") |
| −5 ms from a smaller pool | Measured: **+0.2 ms** | Corpus is ~45 chunks per tenant; retrieval is ~10 ms total — no pool worth shrinking |
| +5% precision | Measured **~+1 to +4 pts** on affected questions, recall unchanged | Positive but within judge noise; end-to-end accuracy unchanged |
| — | Fixed chunker number corruption | Discovered while validating extraction |

## 07 · Configuration reference

| Key | Default | Meaning |
|---|---|---|
| `RETRIEVAL_METADATA_MODE` | `boost` | `off` \| `boost` \| `filter` |
| `RETRIEVAL_META_PRICE_BOOST` | 1.3 | lift for priced chunks on a price question |
| `RETRIEVAL_META_AREA_BOOST` | 1.2 | lift for chunks stating an area on a size question |
| `RETRIEVAL_META_BHK_BOOST` | 1.2 | lift for chunks covering the asked configuration |
| `INGESTION_ENRICH_METADATA` | `true` | tag chunks at ingestion |

**Rollout on any environment:** deploy, then tag existing chunks once —

```bash
docker compose exec core python scripts/backfill_chunk_metadata.py            # dry run + coverage
docker compose exec core python scripts/backfill_chunk_metadata.py --apply
```

Re-ingest any document containing comma-separated number lists to pick up the chunker fix (a
backfill does not re-chunk).

**Debugging a ranking:** `POST /knowledge/search {"query": "..."}` → `metadata` (intent, lifts,
filter, fallback) and per-result `facts` / `meta_boosts`; or `grep rag.meta` in the core logs.

## 09 · Status & out of scope

- **Built, tested, validated on the local stack; not yet committed.**
- **Out of scope, found along the way:**
  - `MAX_CHUNKS_PER_DOC=2` starves multi-tier questions (HI020).
  - `PRICING_MARKERS` matches substrings — `"emi"` fires inside "pr**emi**um".
  - Eval noise: each `--reload` clears the query-embedding cache and OpenAI embeddings drift, flipping
    near-ties between runs (seen on HG138). Pin or persist query vectors for eval runs.
  - `.env.example` contains what look like live Groq / Cerebras keys (PR #39) — rotate and replace
    with placeholders.
- **To prove +5% beyond noise:** a larger price / BHK / area question set, judged over 2–3 runs with a
  paid judge (Groq free tier caps at 200K tokens/day ≈ 13 judged questions).
