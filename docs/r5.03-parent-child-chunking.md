## 2. The problem

Every searchable chunk was up to ~900 characters. A chunk's embedding is roughly the **average** of every fact in it. In the 3 BHK cost sheet, "carpet area of the 1,390 sq ft unit" is a small share of a vector that also means the 1,239 and 1,560 sq ft units, clubhouse charges and car parking. A less relevant but less mixed chunk can outrank it and push the specific fact down, or out of the 8-chunk window the model reads.

The obvious fix, making all chunks small, breaks answers instead: a 200-character fragment loses its table header, its neighbouring sentences and its context.

## 3. What we built

### 3.1 Search small, answer big

```
ingestion   chunk_text() --> PARENT (~900 chars, role=parent, embedded)
                               +--> split_children() --> CHILDREN (~200 chars, role=child, parent_id)

retrieval   (parent_child mode)
            vector list 1 : CHILDREN + standalone   \   each list ranks PARENTS
            vector list 2 : PARENTS  + standalone    >  (a parent = its best hit,
            keyword list  : parents + children + std /   one rank per parent per list)
            --> reciprocal rank fusion across the three lists
            --> existing boosts / per-document cap / min-score run on PARENTS
            --> the model reads the parent's ~900 chars (deduplicated)
```

* **Parents keep their embeddings.** `flat` mode (standalone + parents) is the pre-R5.03 index, and `parent_child` is the new one, **over the same data**. Enabling, A/B testing and rolling back are all a setting change; nothing is re-ingested.
* **Mixed data is safe.** A chunk too small to split, or ingested before R5.03, is `standalone` and is searched in every mode.
* **Fail-safe.** If the parent lookup fails, the matched children are served as-is and the error is logged and traced. A turn never fails because of R5.03.

### 3.2 Data model — migration `0036_parent_child_chunks`

| Column / object | Purpose |
|---|---|
| `chunk_role` text NOT NULL DEFAULT `'standalone'` | `standalone` / `parent` / `child` |
| `parent_id` uuid NULL, FK → `knowledge_chunks.id` ON DELETE CASCADE | A child's parent; deleting a parent can never leave orphaned children |
| `ck_chunks_role`, `ck_chunks_role_parent` | Role is valid; a row has a parent **exactly when** it is a child |
| `ix_chunks_parent` (partial, children only) | Parent lookup and cascade |

Zero-downtime: the columns are metadata-only (PostgreSQL 11+), the constraints are added `NOT VALID` and then validated, and the index is built `CONCURRENTLY`. It is re-runnable. Verified on a fresh database (0001 → 0036) and through a downgrade/upgrade cycle. The model declares the same constraint names, so a database built by `create_all` and one built by upgrading end up identical.

### 3.3 Child splitting (`chunkers.split_children`)

| Parent kind | Children |
|---|---|
| table | header (+ separator) + rows that fit; **every child keeps the column names** |
| list | groups of 3 items (parents use 8), same bullet/comma style |
| prose | small paragraphs merged while they fit; **no overlap across paragraphs** (a cost sheet has one unit per paragraph, and a seam must never carry unit A's total into unit B's child); whole-sentence overlap (100 chars) only inside one long paragraph |

Invariants (unit-tested, and checked on live data by `backfill --verify`):
* **Coverage.** Every sentence, item or row of a parent is in at least one child. Fragments are merged, never dropped.
* **Child-sized chunks are not split.** A chunk of 200 characters or fewer (`CHUNK_CHILD_SPLIT_MIN_CHARS`) stays standalone.
* **Children inherit the heading breadcrumb** ("3 BHK cost sheet", "Amenities > Outdoor").

### 3.4 Retrieval changes (`retrieval.py`, `parent_child.py`)

* **Scope per list.** `RETRIEVAL_PC_VECTOR_SCOPE` / `RETRIEVAL_PC_TEXT_SCOPE` choose what each list searches, applied through a single `chunk_role <> :exclude_role` predicate.
* **Parent-rank fusion (`fuse_parent_rank`).** Within each list, hits are mapped to their parent and parents get dense ranks by their best child. Only then are the lists fused. This fixed the main failure of the first version, where one cost sheet's 5–8 children took 5–8 top keyword ranks ("how many flats in **total**" matches every "Total …" line) and pushed every other document down.
* **Multi-granularity vector search (`separate`).** The query runs against child vectors and against parent vectors as **two lists**, so a section gets one vote for its most precise child and one for its whole-section vector. Children win precise questions; parents win broad ones. Cost: one extra vector query, about 5–10 ms.
* **One batched parent fetch** (a primary-key lookup, scoped by tenant).
* **Cache safety.** The Redis result-cache key includes the mode, scopes and fusion, so flipping a setting never serves the other mode's cached answer.

### 3.5 Deterministic ranking (affects flat mode too)

Many chunks tie on keyword score. Their order was the physical order Postgres returned rows in, which changes on every re-ingest or backfill. **The same question ranked differently after a data rewrite, in flat mode as well.** Fixed with `ORDER BY rank DESC, c.id`, `ORDER BY distance, id`, and Python sorts on `(-score, id)`. Verified: flat results were identical before and after a full rewrite of every parent row.

### 3.6 Extraction-grade ingestion (for a future ingestion service)

Testing on realistic PDF/OCR output exposed defects in the **base chunker**, which assumed clean markdown. All are fixed:

| Extraction shape | Before | Now |
|---|---|---|
| Space-aligned table | read as a comma list; **commas inside numbers were split**: `89,50,000` → `89, 50, 000`. This also hit the **live** DSR "Unit Mix by Tower" chunk (`1, 422 … and 1.`) | converted to a pipe table (header in every child); list splitting never breaks a number |
| Running page header ("Brochure   Page 2") | became the section heading of that page's chunks | removed when repeated on 3+ pages; never treated as a heading |
| Page-number lines | kept as content | removed when 2+ exist |
| Hyphenated wrap `develop-` + newline + `er` | `develop- er` | `developer` |
| Hard-wrapped lines | a wrapped fragment could look like a heading; a wrapped bullet stopped being a list | unwrapped **only when the text shows extraction signals** (`auto`) |
| Unpunctuated run-on text | one unbounded chunk (the embedding provider silently truncates past 8,000 chars) | hard-split at word boundaries |
| Hindi danda | not a sentence end, so Hindi paragraphs never split | a sentence end |
| One failed embedding request | every chunk of the document re-embedded one at a time | only the failed batch (64 texts) is retried |

**Clean documents are unaffected.** All 43 seed documents chunk identically before and after, except the corrected number-comma chunk. The one rule that would change hand-wrapped markdown (unwrapping) only runs when the text shows extraction evidence.

**Contract for an ingestion service:** `ingest_document(db, tenant_id=…, document_id=…, text=…, normalize_mode="always")`, with form feeds (`\f`) between pages if available. The report returns `normalization` (what was changed, with samples), `embedding_batches_retried`, `parent_child_enabled` and parent/child counts.

### 3.7 Per-tenant rollout

The tenant settings JSON overrides the global flags for that tenant only:

```json
{ "chunk_parent_child_enabled": true, "retrieval_granularity": "parent_child" }
```

The value is resolved **once per turn** in the turn context, so there's no extra query on the hot path. An invalid value falls back to the global setting and logs a warning. `POST /knowledge/search` accepts `"granularity"` to compare both modes on one question.

### 3.8 Observability

* **`POST /knowledge/search`** returns a `parent_child` block (`granularity, fusion, vector_scope, text_scope, hits, child_hits, parents, merged_siblings, parents_missing, units, fetch_ms, fetch_error`). Every result also has `matched_children`, the exact ~200-char text(s) that pulled it in, with their ranks.
* **Planner trace** → `retrieval.parent_child` on every knowledge turn.
* **Logs:** `rag.parent_expand …`, `WARNING rag.parent_expand.missing`, `WARNING rag.parent_expand fetch failed`, `ingest.normalize …`, and `ingest doc=… standalone= parents= children= embed_failed= batches_retried=`.
* **`GET /knowledge/documents/{id}`** shows each chunk's `role` and `parent_id`.

## 5. Configuration reference

All settings are environment variables (`.env`), shown with their shipped defaults.

**Ingestion**

| Setting | Default | Meaning |
|---|---|---|
| `INGEST_NORMALIZE_MODE` | `auto` | `auto` (a no-op on clean markdown; unwraps lines only when the text looks extracted), `always`, or `off` |
| `CHUNK_PARENT_CHILD_ENABLED` | `false` | Store parents + children at ingestion. Tenant key: `chunk_parent_child_enabled` |
| `CHUNK_CHILD_TARGET_CHARS` | `200` | Child size |
| `CHUNK_CHILD_OVERLAP_CHARS` | `100` | Sentence overlap, only inside one long paragraph |
| `CHUNK_CHILD_LIST_GROUP_SIZE` | `3` | Items per list child |
| `CHUNK_CHILD_MIN_CHARS` | `40` | Smaller fragments are merged, never dropped |
| `CHUNK_CHILD_SPLIT_MIN_CHARS` | `200` | Chunks at or below this stay standalone |
| `CHUNK_CHILD_TITLE_PREFIX` | `false` | Measured: −4.5 pts Hit@1. Keep off |
| `CHUNK_CHILD_RECORD_SPLIT` | `false` | Measured: lost evidence on 2 questions. Keep off |

**Retrieval**

| Setting | Default | Meaning |
|---|---|---|
| `RETRIEVAL_GRANULARITY` | `flat` | `flat` or `parent_child`. Tenant key: `retrieval_granularity` |
| `RETRIEVAL_PC_VECTOR_SCOPE` | `separate` | `children` / `parents` / `both` / `separate` (two lists) |
| `RETRIEVAL_PC_TEXT_SCOPE` | `both` | `children` / `parents` / `both` |
| `RETRIEVAL_PC_FUSION` | `parent_rank` | `parent_rank` or `child_rank` (the first version, kept for A/B) |
| `RETRIEVAL_PC_PARENT_VECTOR_WEIGHT` | `1.0` | Weight of the parent-vector list in `separate` |
| `RETRIEVAL_PARENT_SIBLING_WEIGHT` / `_CAP` | `0.0` / `0.25` | `child_rank` only; measured best at 0 |
| `RETRIEVAL_PARENT_CHILD_POOL_FACTOR` | `2` | Wider search pool in `parent_child` mode |

**Recommended for DSR today:** `RETRIEVAL_GRANULARITY=flat`. `CHUNK_PARENT_CHILD_ENABLED` may stay `true`: children are only searched when a tenant or the global setting says `parent_child`, and keeping them makes a later switch instant.

After editing `.env`, recreate the container with `docker compose up -d core`. `docker compose restart` does **not** re-read `.env`. No rebuild is needed.

## 6. Applying it to an existing database

Run from the repo root. Every step is safe to re-run.

**1. Deploy the code.** Migration `0036` runs automatically on container start (`alembic upgrade head`). To run it manually:
```bash
docker compose exec core alembic upgrade head
```

**2. Preview the backfill** (dry run: nothing is written; prints the plan and the embedding cost):
```bash
docker compose exec core python scripts/backfill_parent_child.py --show
```

**3. Create children for existing chunks.** Each existing chunk becomes a parent in place. The original document text isn't needed, and each document is its own transaction:
```bash
docker compose exec core python scripts/backfill_parent_child.py --apply
```

**4. Verify integrity and coverage:**
```bash
docker compose exec core python scripts/backfill_parent_child.py --verify
```

**5. Fix the live number-corruption chunk.** Re-ingest the DSR "Unit Mix by Tower" document (re-seed, or `POST /knowledge/documents/{id}/reingest`) so its stored text reads `1,422` instead of `1, 422`.

**6. Run the gate before enabling:**
```bash
docker compose exec core python scripts/eval_parent_child.py --gate
```

**7. Enable,** only if it passes: set `retrieval_granularity` in that tenant's settings, or set `RETRIEVAL_GRANULARITY=parent_child` globally and run `docker compose up -d core`.

**Rollback:** set `RETRIEVAL_GRANULARITY=flat`, which takes effect instantly. To remove the children as well:
```bash
docker compose exec core python scripts/backfill_parent_child.py --revert --apply
```

**Fresh database:** no backfill is ever needed. Set the flags before seeding, and ingestion creates children directly. **Rebuilding children after changing child settings:** `--apply --force`.

## 8. Results

Metrics are **retrieval-only** over the top-8 window: **Complete@8** = every needed fact is in the window (the headline); **Hit@1** = the first passage the model reads carries the answer; **MRR** = mean reciprocal rank of the first evidence-bearing passage.

### 8.1 Tuning journey (44 labelled questions, the tuning set)

| Version | Complete@8 | Hit@1 | MRR | better / worse vs flat |
|---|---|---|---|---|
| flat (production) | 88.6% | 65.9% | 0.755 | – |
| 1. first version (children only, sibling bonus 0.1) | 84.1% | 59.1% | 0.690 | 7 / 11 |
| 2. sibling bonus 0 | 86.4% | 68.2% | 0.773 | 6 / 5 |
| 3. + parent-rank fusion | 86.4% | 70.5% | 0.786 | 6 / 3 |
| 4. + split threshold 200 | 90.9% | 75.0% | 0.821 | 6 / 3 (partly tie-order luck) |
| 5. + deterministic ties | 86.4% | 70.5–72.7% | 0.79–0.81 | 6–7 / 4 |
| **6. final: separate vector lists + keyword over both** | **88.6–90.9%** | **70.5%** | **~0.80** | **6 / 0–1** |

Rejected after measuring: title prefix (−4.5 pts Hit@1), record-boundary splitting (lost evidence on 2 questions), wider pool, larger sibling bonus.

### 8.2 Overfitting checks (settings frozen)

| Question set | Complete@8 | Recall@3 | Hit@1 | MRR | better / worse |
|---|---|---|---|---|---|
| Own holdout, 50 new questions | 96.0 → 94.0% | 86.0 → 86.0% | 74.0 → 76.0% | 0.812 → 0.817 | 4 / 4 |
| Workbook holdout, all 51 | 96.1 → 96.1% | 88.2 → 90.2% | 68.6 → 72.5% | 0.796 → 0.813 | 6 / 3 |
| Workbook holdout, 26 unseen | 96.2 → 96.2% | 84.6 → 88.5% | 61.5 → 65.4% | 0.754 → 0.767 | 4 / 3 |
| **Pooled, independent questions** | level (±1 question) | | **+2 to +5 pts** | | **14 / 8, p≈0.29** |

**Where it wins:** precise facts inside dense chunks, e.g. a unit's facing, carpet area and building height ("1 basement plus ground plus 12 floors" was found only in parent-child mode).
**Where it loses:** (a) short standalone summary/policy chunks outcompeted by many precise children of long priced documents ("How many flats in total?", "price of the 1.5 BHK?"); (b) the 2-chunks-per-document cap, when a sibling section matches a stray word ("creche for young **children**" → Outdoor's "Children's play area" displaced the Indoor section).

### 8.3 End-to-end spot check (Groq `gpt-oss-120b` judge, free tier, 11 questions)

| | Passed |
|---|---|
| Baseline, 25 Sep (flat, gpt-4o judge) | 10 / 11 |
| Parent-child, 30 Sep | 8 / 11 |

* **EN027** ("How many flats in total?"): the predicted retrieval loss became a wrong answer ("I don't have the total number of flats").
* **EN053**: the agent said "construction is ongoing", which the KB doesn't state. That's a responder invention on a question the KB can't answer, and probably normal run-to-run variation.
* **EN016** fails in both runs: the responder claims the fund is "not refundable", which the KB doesn't say.
* This is not conclusive (different judges, different days, no same-day flat run, n=11), but it is consistent with the retrieval results.

### 8.4 Latency and cost

* Retrieval p50: flat ~15 ms, parent-child ~20–28 ms (extra vector list + parent fetch of ~1–2 ms).
* OpenAI spend for the whole task: about $0.001 (child embeddings for several re-backfills, plus ~110 new query embeddings). Every retrieval-eval re-run is $0.

## 9. Verdict

1. **For DSR, keep `RETRIEVAL_GRANULARITY=flat`.** Parent-child gives a small, consistent ranking gain but no coverage gain and no measurable accuracy gain on this KB, and it adds ~10 ms per retrieval. It isn't overfitted and it isn't harmful. It just isn't worth switching on here.
2. **Why the estimated +8–12% didn't happen here.** That estimate assumed 900-character chunks mixing many facts. The DSR KB is 16 hand-written documents (44 chunks, averaging 428 characters), and the structure-aware chunker already splits lists and tables. There is little averaging left for R5.03 to fix.
3. **Likely more valuable on large or dense corpora** (extracted brochures, long price lists, spec and legal PDFs, many near-duplicate documents), which is where every observed win came from. Treat that as a hypothesis to test per tenant: ingest with children → `build_retrieval_qrels.py --apply` → human review → `eval_parent_child.py --gate --qrels-file …` → enable for that tenant only.
4. **Keep, and ship on regardless of the switch:** the number-safe chunking (fixes live price corruption; re-ingest "Unit Mix by Tower"), deterministic ranking, extraction-grade ingestion, resilient embedding, and the evaluation harness.

## 10. Known limitations and next steps

* **Short standalone chunks vs many children.** The main systematic loss. It's worth trying only with a fresh holdout, since the three sets above have now been looked at.
* **Per-document cap of 2.** Drops the right section when a sibling section matches a stray word. R5.01 found cap 3 helps together with reranking; evaluate them together after merging.
* **`eval_rag_accuracy.py --compare` doesn't check the judge model.** A run graded by a different judge can be compared silently. Add a guard once the R5.01 branch is merged (the file is shared).
* **Merging with R5.01 (reranker):** rerank after fusion on parent units, scoring (query, best matched child), which `matched_children` already carries.
* **Merging with R5.08 (metadata enrichment):** tag price/BHK facts on children too, since the pre-filter must see the rows that are searched.
* **End-to-end A/B not completed** (Groq free-tier limit: 8,000 tokens/min). The procedure is to run the same `--ids` with the same judge in both modes, using `--compare`.
