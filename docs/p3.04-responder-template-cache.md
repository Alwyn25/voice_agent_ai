# P3.04 — Response Caching: Skip the Responder LLM for High-Confidence Tool Results

**Owner:** Nikhil · **Phase:** 3 (TTFA < 500 ms) · **Stage:** RSP · **Status:** Implemented (2026-09-21)
**Feature flag:** `RESPONDER_TEMPLATE_CACHE_ENABLED` (off by default)

---

## 1. The Problem

On every tool turn, after a tool executes, the turn runner calls the **responder LLM**
(`responder.generate`) to phrase the customer-facing reply. This is the **RSP stage** — a
full LLM round-trip on *every* tool turn, plus a per-call token cost.

For a large class of outcomes, that reply is **deterministic**. When `book_appointment`
succeeds, the honest reply is always *"Your visit is confirmed for &lt;day&gt; at
&lt;time&gt;…"* — and every fact in it (the slot, the centre, the status) is already sitting
in the tool's own output. Paying for an LLM round-trip to re-phrase a fixed confirmation is
pure latency waste.

Measured live, the responder call was costing **~1.0–1.7 seconds** per tool turn. Eliminating
it on deterministic confirmations is the P3.04 objective.

---

## 2. The Solution

A **template cache**: when a write/confirm tool genuinely completes, render its confirmation
directly from the tool output — in the caller's language — with **no model call**.

### 2.1 Where it lives

| File | Role |
| :--- | :--- |
| `core/app/engine/voice/templated_reply.py` | **New.** Pure `render()` — templates, eligibility gate, logging. No DB / LLM / pipecat. |
| `core/app/config.py` | **New flag** `responder_template_cache_enabled` (default `False`). |
| `core/app/engine/planner/turn_runner.py` | **Wiring.** Wraps the single `responder.generate` call site in an `if template / else LLM` branch, plus observability. |
| `core/tests/test_templated_reply.py` | **New.** 18 unit tests (per tool × language + fail-safe cases). |

### 2.2 How a turn is served

```
tool executes  ->  templated_reply.render(outcome, action_state, language, reframing)
                      |
        +-------------+--------------------------------+
        |                                              |
   returns a reply (deterministic)              returns None (anything off)
        |                                              |
   text + grounded meta                        responder.generate(...)  <- LLM, unchanged
   responder_ms = 0                            responder_ms ~= 1000-1700
        |                                              |
        +----------------------> downstream guards <---+
             (wrong-slot check, grounding_check, price rounding, closer trims)
                                        |
                                     TTS / reply
```

### 2.3 Eligibility — a template is used only when ALL hold

- The feature flag is on.
- A tool outcome exists and its status is a success (`success` / `skipped_duplicate`).
- The action **genuinely completed** (`action_state == "done"` — never `staged` / `blocked`
  / `failed`).
- The tool is in the allow-list (the 7 write/confirm tools below).
- No "reframing" signal is active (a presence-check continuation, a pitch-ladder rung, a
  forced project-disambiguation, or an outbound lead line — those need the LLM).
- The renderer produced text with every required field present.

If any condition misses, `render()` returns `None` and the LLM path runs exactly as before —
**fail-safe by construction.**

### 2.4 Covered tools

`book_appointment`, `reschedule_appointment`, `cancel_appointment`, `schedule_callback`,
`create_ticket`, `record_do_not_contact`, `send_document` — each with a fixed confirmation in
**English, Hindi, and Hinglish**, matched to the caller's turn language.

### 2.5 Why it is safe

The templated text is substituted for the LLM's, and then **every existing post-responder
guard still runs on it** — the wrong-slot date/time check, `grounding_check`, the scope /
visit-claim guards, price rounding, and the repeated-closer trims. The template goes through
the identical validation net an LLM reply would, so it cannot regress correctness. The reply's
meta is shaped exactly like the responder's healthy grounded return, so those guards behave
identically.

### 2.6 Enable / disable

One environment variable controls the whole feature:

```
RESPONDER_TEMPLATE_CACHE_ENABLED=true
```

Set it and restart the voice server to activate; unset it to roll back instantly with zero
code change.

### 2.7 Observability

- **Logger** `app.engine.voice.templated_reply`: a hit logs
  `template hit: book_appointment.english served deterministically (RSP LLM skipped)`; a skip
  logs the exact reason.
- **Turn timing** (in the existing `voice turn done` log): `responder_ms` becomes `0`,
  `responder_source` = `template` vs `llm`, and `responder_template` names the exact template
  that fired.

## 3. Results

Measured live on a real booking-confirmation turn (the caller says "yes" to confirm the
staged `book_appointment`), flag **enabled** vs **disabled**.

### 3.1 Latency comparison

| Metric (booking confirm turn) | Disabled (LLM) | Enabled (template) | Change |
| :--- | ---: | ---: | ---: |
| Responder stage `responder_ms` | 1,733 ms | **0 ms** | **−1,733 ms** |
| `responder_source` | `llm` | `template` | — |
| Total turn `total_ms` | 4,423 ms | **3,505 ms** | **−918 ms** |
| Tool execution `tool_ms` | 109 ms | 118 ms | ~same |

The responder LLM round-trip is **eliminated entirely** on the confirmation turn. The RSP
stage drops from 1,733 ms to 0, and end-to-end turn time falls by ~918 ms.

### 3.2 Reply comparison (same booking intent)

**Disabled (responder LLM):**

> Your appointment is successfully booked for the 2 BHK at DSR Highland Greenz — Site Office
> on September 22, 2026, starting at 11:00 AM. Looking forward to seeing you there!

**Enabled (template):**

> Your visit is confirmed for Tuesday, 22 September at 10:00 AM, at DSR Highland Greenz —
> Site Office.

Both are grounded, correct confirmations naming the real booked slot and centre. The template
is a single, tight sentence; the fact content is identical.

### 3.3 Log evidence (enabled)

## 5. Summary

P3.04 removes the responder LLM from deterministic write/confirm tool turns via a
language-matched template renderer. It is production-grade (fail-safe fallback, all safety
guards preserved), controlled by a single environment variable, and fully observable. On a
live booking-confirmation turn it eliminated a **1,733 ms** responder call and cut total turn
latency by **~918 ms**.
